# 4.6.5 | Firebase, Cloud Functions and Security

This subsection documents the cross-cutting backend layer that enforces Jirani’s security model beyond individual resident and administrator screens. Firestore Security Rules are maintained as modular fragments and assembled into a single deployable `firestore.rules` file. Cloud Functions run with the Firebase Admin SDK to perform privileged writes that clients cannot perform directly — including public profile mirroring, verification status sync, in-app and push notifications, blind review publishing, Community Trust Score recalculation, registration finalization, and Xendit payment settlement. The Flutter client activates Firebase App Check on mobile to reduce abuse of callable functions and backend resources. Together, these layers implement a defense-in-depth pattern: rules constrain what authenticated clients may read or write, while functions own sensitive state transitions and side effects.

## | Modular Firestore Security Rules Assembly

**Figure 4.xxx: Firestore Rules Build Script**

Figure 4.xxx presents `scripts/build_firestore_rules.mjs`, which assembles all fragments under `firestore_rules/*.rules` into the generated root `firestore.rules` file. Fragments are sorted lexicographically so helper functions are defined before collection matchers that depend on them. The build script writes a generated-file header reminding developers to edit fragments rather than the assembled output. This modular structure keeps verification, marketplace, chat, and review policies maintainable as the platform grows, and ensures the deployed rules always match the version-controlled source fragments.

**Code sample to screenshot** — `scripts/build_firestore_rules.mjs`

```javascript
function build() {
  const files = fs
    .readdirSync(rulesDir)
    .filter((f) => f.endsWith('.rules'))
    .sort();

  const fragments = files.map((f) =>
    fs.readFileSync(path.join(rulesDir, f), 'utf8').trim(),
  );

  const body = fragments.join('\n\n');
  const output = `${GENERATED_HEADER}
rules_version = '2';

service cloud.firestore {
  match /databases/{database}/documents {
${body}
  }
}
`;

  fs.writeFileSync(outFile, output, 'utf8');
  const lineCount = output.split(/\r?\n/).length;
  console.log(`Wrote ${outFile} (${lineCount} lines)`);
}
```

## | Core Authentication and Administrator Helper Functions

**Figure 4.xxx: Firestore Core Security Helpers**

Figure 4.xxx presents the shared helper functions in `01_core.functions.rules` that underpin every collection rule. `signedIn()` and `isOwner(uid)` establish basic authentication checks. `myUserDoc()` and `myAdminDoc()` load the caller’s profile documents for role and community evaluation. `isAdmin()` and `isSystemAdmin()` validate active administrator accounts and roles. `adminCanAccessCommunity(communityId)` scopes community administrators to their assigned community while allowing system administrators global access. `isVerifiedResident()` gates community features so only residents with `verificationStatus` of `verified` or `approved` may access neighbor-facing data. These helpers are reused across users, verification, marketplace, chat, and report matchers to keep authorization logic consistent.

**Code sample to screenshot** — `firestore_rules/01_core.functions.rules` (lines 1–98)

```javascript
function signedIn() {
  return request.auth != null;
}

function isOwner(uid) {
  return signedIn() && request.auth.uid == uid;
}

function myUserDoc() {
  return get(/databases/$(database)/documents/users/$(request.auth.uid));
}

function myAdminDoc() {
  return get(/databases/$(database)/documents/admins/$(request.auth.uid));
}

function isAdmin() {
  return hasAdminProfile() && isValidAdminDoc(myAdminDoc().data);
}

function isSystemAdmin() {
  return hasAdminProfile() &&
    isValidAdminDoc(myAdminDoc().data) &&
    adminRole(myAdminDoc().data) == 'systemAdmin';
}

function adminCanAccessCommunity(communityId) {
  return isSystemAdmin() ||
    (
      isAdmin() &&
      communityId is string &&
      communityId != '' &&
      communityId == adminCommunityId()
    );
}

function isVerifiedResident() {
  return hasProfile() &&
    hasVerifiedResidentStatus(myUserDoc().data.verificationStatus);
}

function canReadCommunityResident(data) {
  return isVerifiedResident() &&
    isVerifiedResidentData(data) &&
    data.communityId == myUserDoc().data.communityId;
}
```

## | Users, Public Profiles, and Phone Registry Rules

**Figure 4.xxx: Users Collection Security Rules**

Figure 4.xxx presents the Firestore matchers for `users`, `publicProfiles`, `admins`, `communities`, and `residentPhoneNumbers`. Residents may create their own profile only with `role == 'resident'` and `verificationStatus == 'pending'`. Trust and reputation fields on `users/{uid}` are never writable by residents — only administrators or Cloud Functions using the Admin SDK may update them. `publicProfiles/{uid}` exposes community-safe resident fields and is readable by verified neighbors in the same community; writes are admin-only because the collection is synchronized from `users` by a Cloud Function. The `residentPhoneNumbers` registry is fully denied to clients so phone uniqueness is enforced exclusively through backend callables during registration and phone updates.

**Code sample to screenshot** — `firestore_rules/10_collections_users.rules`

```javascript
match /users/{uid} {
  allow get: if isOwner(uid) || isAdmin();
  allow list: if isSystemAdmin() ||
    (isAdmin() && resource.data.communityId == adminCommunityId());

  allow create: if isOwner(uid) &&
    request.resource.data.uid == uid &&
    request.resource.data.role == 'resident' &&
    request.resource.data.verificationStatus == 'pending';

  // Trust/reputation fields are updated only by Cloud Functions (Admin SDK)
  // or manually by admins — never by resident clients.
  allow update: if isAdmin() ||
    (isOwner(uid) && ownSafeUserUpdate() && validResidentSelfProfileData()) ||
    (isOwner(uid) && ownerCanChangeCommunityWithVerificationReset());
  allow delete: if isAdmin();
}

match /publicProfiles/{uid} {
  allow get: if isOwner(uid) ||
    isAdmin() ||
    canReadPublicProfile(resource.data);
  allow list: if isVerifiedResident() &&
    resource.data.communityId == myUserDoc().data.communityId;
  allow create, update, delete: if isAdmin();
}

match /residentPhoneNumbers/{phoneHash} {
  allow read, write: if false;
}
```

## | Verification Request Security Rules

**Figure 4.xxx: Verification Requests Collection Rules**

Figure 4.xxx presents the `verificationRequests` collection rules. Residents may read only their own requests; administrators may read requests within their community scope. Creation is validated through `validVerificationCreate()` so submitted payloads include required community and document fields. Residents may update only to cancel a request or replace an uploaded document URL while keeping status unchanged — they cannot self-approve verification. Final approval and rejection remain administrator actions enforced both in client UI and in these rules. This separation ensures residency proof cannot be escalated to `verified` from the mobile client.

**Code sample to screenshot** — `firestore_rules/11_collections_verification.rules`

```javascript
match /verificationRequests/{requestId} {
  allow read: if signedIn() &&
    (
      resource.data.userId == request.auth.uid ||
      isSystemAdmin() ||
      adminCanAccessCommunity(resource.data.communityId)
    );

  allow create: if signedIn() &&
    validVerificationCreate(request.resource.data);

  allow update: if isAdmin() ||
    (
      signedIn() &&
      resource.data.userId == request.auth.uid &&
      (
        (
          request.resource.data.diff(resource.data).affectedKeys().hasOnly([
            'status',
            'cancelledAt',
            'cancelledBy',
          ]) &&
          request.resource.data.status == 'cancelled' &&
          request.resource.data.cancelledBy == request.auth.uid
        ) ||
        (
          request.resource.data.diff(resource.data).affectedKeys().hasOnly([
            'documentUrl',
            'fileUrl',
            'updatedAt',
          ]) &&
          request.resource.data.userId == resource.data.userId &&
          request.resource.data.status == resource.data.status &&
          request.resource.data.storagePath == resource.data.storagePath
        )
      )
    );

  allow delete: if isAdmin();
}
```

## | Marketplace and Service Collection Rules

**Figure 4.xxx: Marketplace and Service Security Rules**

Figure 4.xxx presents the Firestore matchers for `items`, `borrowRequests`, `services`, and `serviceRequests`. Marketplace listings are readable through `canReadMarketplaceItem()` and writable only by verified owners using validated create and update helpers. Borrow and service requests are readable only by the participating borrower/requester, owner/provider, or a scoped administrator. Updates pass through `validBorrowRequestUpdate()` and `validServiceRequestUpdate()` so clients cannot skip lifecycle states — for example, marking a borrow completed or changing deposit fields without going through the payment callable. Administrators retain override access for moderation and dispute resolution.

## | Reviews, Reports, and Default Deny Rules

**Figure 4.xxx: Reviews and Reports Security Rules**

Figure 4.xxx presents the security model for `reviews` and `reports`. Reviews are created through validated client writes or callable functions, but publishing (`visible: true`, `status: 'published'`) is restricted to administrators and Cloud Functions — this supports the blind review pattern where both parties submit hidden reviews before either becomes public. Residents may read published reviews and their own hidden submissions. Reports are readable and writable only by scoped administrators; residents may create reports through `validReportCreate()`. The `match /{document=**}` default deny at the end of `18_collections_community.rules` blocks access to any collection not explicitly defined, closing accidental data exposure paths.

**Code sample to screenshot** — `firestore_rules/13_collections_reviews_reports.rules` and `firestore_rules/18_collections_community.rules` (lines 38–40)

```javascript
match /reviews/{reviewId} {
  allow get: if signedIn() &&
    (
      !exists(/databases/$(database)/documents/reviews/$(reviewId)) ||
      reviewId.matches('.*_' + request.auth.uid) ||
      isAdmin() ||
      resource.data.visible == true
    );
  allow list: if signedIn() &&
    (
      isAdmin() ||
      resource.data.visible == true ||
      resource.data.reviewerId == request.auth.uid
    );
  allow create: if validReviewCreate(reviewId, request.resource.data);
  // Publishing is handled server-side by Cloud Functions.
  allow update: if isAdmin();
  allow delete: if isAdmin();
}

match /reports/{reportId} {
  allow read: if isSystemAdmin() ||
    adminCanAccessCommunity(resource.data.communityId) ||
    (isAdmin() && !resource.data.keys().hasAny(['communityId']));

  allow create: if hasProfile() &&
    validReportCreate(request.resource.data);

  allow update, delete: if isSystemAdmin() ||
    adminCanAccessCommunity(resource.data.communityId) ||
    (isAdmin() && !resource.data.keys().hasAny(['communityId']));
}

match /{document=**} {
  allow read, write: if false;
}
```

**Figure 4.xxx: Chat Collection Security Rules**

## | Resident Self-Profile Update Constraints

**Figure 4.xxx: Safe Resident Profile Update Rules**

Figure 4.xxx presents `ownSafeUserUpdate()` and `ownerCanChangeCommunityWithVerificationReset()` in `05_user.functions.rules`. The `ownSafeUserUpdate()` helper whitelists only non-privileged profile fields — name, contact preferences, permission toggles, FCM token, and location verification metadata. Residents cannot directly modify `verificationStatus`, trust scores, completion counters, or account flags. When a resident changes community, `ownerCanChangeCommunityWithVerificationReset()` requires `verificationStatus` to reset to `pending` and location verification to clear, forcing re-verification in the new community. These field-level constraints complement the users collection matcher shown earlier.

**Code sample to screenshot** — `firestore_rules/05_user.functions.rules`

```javascript
function ownSafeUserUpdate() {
  let changed = request.resource.data.diff(resource.data).affectedKeys();
  return changed.hasOnly([
    'firstName',
    'lastName',
    'fullName',
    'email',
    'pendingEmail',
    'emailVerified',
    'profileImageUrl',
    'communityId',
    'communityName',
    'unitNumber',
    'cameraEnabled',
    'cameraPermissionStatus',
    'photosDocumentsEnabled',
    'photosDocumentsPermissionStatus',
    'notificationEnabled',
    'notificationPermissionStatus',
    'neighborUpdatesEnabled',
    'fcmToken',
    'locationVerified',
    'locationVerificationStatus',
    'locationVerifiedCommunityName',
    'updatedAt',
  ]);
}

function ownerCanChangeCommunityWithVerificationReset() {
  let changed = request.resource.data.diff(resource.data).affectedKeys();
  return changed.hasAll(['communityId', 'communityName']) &&
    changed.hasOnly([
      'communityId',
      'communityName',
      'verificationStatus',
      'locationVerified',
      'locationVerificationStatus',
      'locationVerifiedCommunityName',
      'updatedAt',
    ]) &&
    resource.data.communityId != request.resource.data.communityId &&
    request.resource.data.verificationStatus == 'pending' &&
    request.resource.data.locationVerified == false &&
    request.resource.data.locationVerificationStatus == 'pending' &&
    request.resource.data.locationVerifiedCommunityName == '' &&
    request.resource.data.updatedAt == request.time;
}
```

## | Public Profile Synchronization

**Figure 4.xxx: Public Profile Sync Function**

Figure 4.xxx presents `buildPublicProfilePayload()` and `syncPublicProfileFromUser()` in `public_profile.ts`. Whenever `users/{uid}` is written, the `syncPublicResidentProfile` trigger rebuilds a safe `publicProfiles/{uid}` document containing only community-visible fields — name, avatar, community, verification status, trust metrics, and completion counters. Private fields such as email, phone, FCM token, and permission flags are excluded. If the user is deleted or no longer a resident, the public profile document is removed. This pattern lets verified neighbors query lightweight profile data without exposing sensitive account information, while Firestore rules on `publicProfiles` remain admin-write-only.

**Code sample to screenshot** — `functions/src/public_profile.ts` (lines 44–105)

```typescript
export function buildPublicProfilePayload(
  uid: string,
  data: DocumentData,
): DocumentData | null {
  if (data.role !== "resident" || data.accountStatus === "deleted") {
    return null;
  }

  const names = parseName(data);
  const fullName = `${names.firstName} ${names.lastName}`.trim();
  const verificationStatus = normalizeVerificationStatus(data.verificationStatus);

  return {
    uid,
    firstName: names.firstName,
    lastName: names.lastName,
    fullName,
    profileImageUrl:
      typeof data.profileImageUrl === "string" ? data.profileImageUrl : "",
    communityId: typeof data.communityId === "string" ? data.communityId : "",
    communityName:
      typeof data.communityName === "string" ? data.communityName : "",
    role: "resident",
    verificationStatus,
    accountStatus:
      typeof data.accountStatus === "string" ? data.accountStatus : "active",
    reputationScore: asNumber(data.reputationScore),
    communityTrustScore: asNumber(
      data.communityTrustScore ?? data.reputationScore,
    ),
    totalReviews: asInt(data.totalReviews),
    trustedResident: data.trustedResident === true,
    completedBorrowings: asInt(data.completedBorrowings),
    completedLendings: asInt(data.completedLendings),
    completedServices: asInt(data.completedServices),
    completedServicesProvided: asInt(data.completedServicesProvided),
    completedServicesRequested: asInt(data.completedServicesRequested),
    updatedAt: admin.firestore.FieldValue.serverTimestamp(),
  };
}

export async function syncPublicProfileFromUser(
  db: admin.firestore.Firestore,
  uid: string,
  data: DocumentData | undefined,
): Promise<void> {
  const publicRef = db.collection("publicProfiles").doc(uid);

  if (!data) {
    await publicRef.delete().catch(() => undefined);
    return;
  }

  const payload = buildPublicProfilePayload(uid, data);
  if (!payload) {
    await publicRef.delete().catch(() => undefined);
    return;
  }

  await publicRef.set(payload, { merge: false });
}
```

## | Verification Request User Synchronization

**Figure 4.xxx: Verification Sync Trigger**

Figure 4.xxx presents the verification synchronization pipeline in `verification_sync.ts` and its `onVerificationRequestUserSync` trigger. When a resident submits a verification request with an uploaded document, `verificationRequestBecameReady()` detects the transition and `syncUserFromSubmittedVerificationRequest()` mirrors `communityId`, `communityName`, `unitNumber`, and `verificationStatus: "submitted"` onto `users/{uid}`. If the resident cancels the request, `syncUserFromCancelledVerificationRequest()` resets `verificationStatus` back to `pending` when appropriate. This keeps the resident profile and verification queue aligned without allowing the mobile client to write verification status directly.

**Code sample to screenshot** — `functions/src/verification_sync.ts` and `functions/src/index.ts` (lines 393–417)

```typescript
export function verificationRequestBecameReady(
  before: DocumentData | undefined,
  after: DocumentData | undefined,
): boolean {
  return (
    !verificationRequestReadyForUserSync(before) &&
    verificationRequestReadyForUserSync(after)
  );
}

export async function syncUserFromSubmittedVerificationRequest(
  db: Firestore,
  data: DocumentData,
): Promise<void> {
  const userId = data.userId;
  if (typeof userId !== "string" || userId.length === 0) return;

  const userRef = db.collection("users").doc(userId);
  const userSnap = await userRef.get();
  if (!userSnap.exists) return;

  const currentStatus = userSnap.data()?.verificationStatus;
  if (currentStatus === "verified") return;

  const updates: DocumentData = {
    verificationStatus: "submitted",
    updatedAt: admin.firestore.FieldValue.serverTimestamp(),
  };

  if (typeof data.communityId === "string" && data.communityId.length > 0) {
    updates.communityId = data.communityId;
  }
  if (typeof data.communityName === "string") {
    updates.communityName = data.communityName;
  }
  if (typeof data.unitNumber === "string") {
    updates.unitNumber = data.unitNumber;
  }

  await userRef.update(updates);
}

// index.ts trigger
export const onVerificationRequestUserSync = onDocumentWritten(
  "verificationRequests/{requestId}",
  async (event) => {
    const before = event.data?.before.data();
    const after = event.data?.after.data();
    const db = admin.firestore();

    if (verificationRequestBecameReady(before, after) && after) {
      await syncUserFromSubmittedVerificationRequest(db, after);
    }

    if (verificationRequestBecameCancelled(before, after) && after) {
      await syncUserFromCancelledVerificationRequest(db, after);
    }
  },
);
```

## | In-App and Push Notification Pipeline

**Figure 4.xxx: Notification Creation and FCM Delivery**

Figure 4.xxx presents the shared notification helpers in `notifications.ts`. Domain-specific triggers (borrow, chat, connection, service, community post, report) call `createInAppNotification()` or `createInAppNotificationIfAbsent()` with deterministic IDs to prevent duplicate fan-out on retries. The `onNotificationCreatedSendPush` trigger then reads the recipient’s `fcmToken` and notification preferences from `users/{uid}` before sending an FCM message through `getMessaging().send()`. Invalid tokens are cleared automatically when Firebase returns `messaging/registration-token-not-registered`. Neighbor activity notifications respect the `neighborUpdatesEnabled` preference. This two-step pipeline separates in-app inbox persistence from device push delivery.

**Code sample to screenshot** — `functions/src/notifications.ts` (lines 105–144, 147–241)

```typescript
export async function createInAppNotificationIfAbsent(
  db: Firestore,
  notificationId: string,
  input: InAppNotificationInput,
): Promise<string | null> {
  if (!input.userId || input.userId === input.actorId) {
    return null;
  }

  const ref = db.collection("notifications").doc(notificationId);
  const payload = buildNotificationPayload(input);

  try {
    await ref.create(payload);
    return ref.id;
  } catch (error) {
    if (isAlreadyExistsError(error)) {
      return ref.id;
    }
    throw error;
  }
}

export async function sendFcmForNotification(
  db: Firestore,
  notification: DocumentData,
): Promise<void> {
  const userId = notification.userId;
  if (typeof userId !== "string" || userId.length === 0) return;

  const userSnap = await db.collection("users").doc(userId).get();
  const userData = userSnap.data();
  if (userData?.notificationEnabled === false) {
    return;
  }

  const fcmToken = userData?.fcmToken;
  if (typeof fcmToken !== "string" || fcmToken.trim().length === 0) {
    return;
  }

  const title =
    typeof notification.title === "string" ? notification.title : "Jirani";
  const body = typeof notification.body === "string" ? notification.body : "";

  try {
    await getMessaging().send({
      token: fcmToken.trim(),
      notification: { title, body },
      data: { /* chatId, borrowRequestId, etc. */ },
    });
  } catch (error) {
    const code = (error as { code?: string }).code;
    if (code === "messaging/registration-token-not-registered") {
      await db.collection("users").doc(userId).update({
        fcmToken: admin.firestore.FieldValue.delete(),
      });
      return;
    }
    throw error;
  }
}
```

## | Blind Review Publishing

**Figure 4.xxx: Marketplace Review Publish Logic**

Figure 4.xxx presents the blind review system in `review_publish.ts` and related triggers. Residents submit reviews through the `createMarketplaceReview` callable, which stores reviews as `visible: false` with `status: "hidden"` and sets a three-day grace period on the borrow request. `publishEligibleReviewsForBorrowRequest()` runs inside a Firestore transaction: when both parties have submitted or the grace period expires, hidden reviews are flipped to `visible: true` and `status: "published"`, and `reviewsPublishedAt` is stamped on the borrow request. A scheduled `publishExpiredBorrowReviews` job provides a fallback for requests whose grace window passed without a triggering document update. Firestore rules block clients from performing this publish step directly.

**Code sample to screenshot** — `functions/src/review_publish.ts` (lines 47–110) and `functions/src/index.ts` (lines 428–468)

```typescript
export async function publishEligibleReviewsForBorrowRequest(
  db: Firestore,
  borrowRequestId: string,
): Promise<void> {
  const reqRef = db.collection("borrowRequests").doc(borrowRequestId);

  await db.runTransaction(async (txn) => {
    const reqSnap = await txn.get(reqRef);
    if (!reqSnap.exists) return;

    const reqData = reqSnap.data()!;
    if (reqData.status !== "completed") return;
    if (reqData.reviewsPublishedAt) return;

    const borrowerSubmitted = reqData.borrowerReviewSubmitted === true;
    const ownerSubmitted = reqData.ownerReviewSubmitted === true;
    if (!borrowerSubmitted && !ownerSubmitted) return;

    const hasBothReviews = borrowerSubmitted && ownerSubmitted;
    const graceExpired = isGraceExpired(reqData.reviewGraceEndsAt);
    if (!hasBothReviews && !graceExpired) return;

    // ... collect pending hidden review refs ...

    for (const reviewRef of pendingReviewRefs) {
      txn.update(reviewRef, {
        visible: true,
        status: "published",
        publishedAt: admin.firestore.FieldValue.serverTimestamp(),
      });
    }

    txn.update(reqRef, {
      reviewsPublishedAt: admin.firestore.FieldValue.serverTimestamp(),
      updatedAt: admin.firestore.FieldValue.serverTimestamp(),
    });
  });
}
```

## | Community Trust Score Recalculation

**Figure 4.xxx: Trust Score Recalculation After Review Publish**

Figure 4.xxx presents `recalculateTrustScoreForUser()` in `trust_score.ts` and the `onReviewPublished` trigger. When a review transitions from hidden to published, `reviewBecamePublished()` returns true and the trigger recalculates a time-weighted Community Trust Score from all visible reviews for the reviewee. Recent reviews carry more weight through a decay function (`weight = 1 / (1 + ageDays / 90)`). The function updates `communityTrustScore`, `totalReviews`, `trustedResident`, and `accountFlagged` on `users/{uid}` — fields that residents cannot modify through Firestore rules. Scores below 3.5 automatically create a low-trust admin report; one-star damage reviews from lenders can create damage reports for moderator review.

**Code sample to screenshot** — `functions/src/trust_score.ts` (lines 55–112, 223–230) and `functions/src/index.ts` (lines 471–506)

```typescript
export async function recalculateTrustScoreForUser(
  db: Firestore,
  userId: string,
  triggerReviewId: string,
): Promise<void> {
  const reviewsSnap = await db
    .collection("reviews")
    .where("revieweeId", "==", userId)
    .where("visible", "==", true)
    .get();

  if (reviewsSnap.empty) {
    return;
  }

  const now = new Date();
  let weightedTotal = 0;
  let weightSum = 0;

  for (const doc of reviewsSnap.docs) {
    const review = doc.data() as ReviewData;
    const rating = typeof review.rating === "number" ? review.rating : 0;
    const createdAt = reviewCreatedAt(review);
    const ageDays = Math.min(
      3650,
      Math.max(0, Math.floor((now.getTime() - createdAt.getTime()) / 86_400_000)),
    );
    const weight = 1 / (1 + ageDays / 90);
    weightedTotal += rating * weight;
    weightSum += weight;
  }

  const totalReviews = reviewsSnap.size;
  const trustScore = weightSum === 0 ? 0 : weightedTotal / weightSum;
  const trustedResident =
    trustScore >= TRUSTED_RESIDENT_THRESHOLD &&
    totalReviews >= TRUSTED_RESIDENT_MINIMUM_REVIEWS;
  const accountFlagged = trustScore < LOW_TRUST_THRESHOLD;

  await db.collection("users").doc(userId).update({
    reputationScore: trustScore,
    communityTrustScore: trustScore,
    totalReviews,
    trustedResident,
    accountFlagged,
    trustFlagReason: accountFlagged
      ? `Community Trust Score dropped below ${LOW_TRUST_THRESHOLD.toFixed(1)}.`
      : "",
    lastTrustReviewId: triggerReviewId,
    trustScoreUpdatedAt: admin.firestore.FieldValue.serverTimestamp(),
    updatedAt: admin.firestore.FieldValue.serverTimestamp(),
  });
}

export function reviewBecamePublished(
  before: ReviewData | undefined,
  after: ReviewData | undefined,
): boolean {
  if (!before || !after) return false;
  const wasPublished = before.visible === true && before.status === "published";
  const isPublished = after.visible === true && after.status === "published";
  return !wasPublished && isPublished;
}
```
